# 개발 회고 — Lessons Learned

이 프로젝트(PHM 오토인코더 이상탐지 웹앱)를 만들면서 **실제로 겪은 시행착오**를 정리한
문서다. 목적은 반성이 아니라 **다음 앱(예: iPhone 앱)에서 같은 실수를 반복하지 않는 것**이다.

각 항목은 아래 형식으로 쓴다.

> **무슨 일이 있었나** → **근본 원인** → **다음엔 이렇게** → **📱 iPhone 앱에서는**

마지막 4부의 **킥오프 체크리스트**는 새 프로젝트 첫날에 그대로 복사해 쓰는 용도다.

| 8 | UI 자동화 테스트를 텍스트/인덱스로 지정 | 테스트가 계속 깨짐 | **안정적 식별자**를 UI에 심는다 |

# 1부. 실제로 겪은 시행착오

## L1. 화면 구조를 정하지 않고 기능부터 붙였다 (가장 비쌌다)

**무슨 일이 있었나**
기능을 요청받는 대로 한 페이지에 계속 쌓았다. 결과적으로 레이아웃을 세 번 갈아엎었다.
① 단일 스크롤 페이지 → ② 상단 고정 컨트롤 + EDA/학습 결과 가로 프레임 분할
(`acf655e`) → ③ 좌측 4메뉴 내비게이션 (`083719b`) → ④ 사이드바 중복 정리 (`67cf314`).
"버튼을 찾으려고 화면을 상하로 왔다 갔다 해야 한다"는 피드백이 나온 뒤에야 구조 문제임을
인정했다.

**근본 원인**
기능 단위로만 사고했고, **정보 구조(IA)를 산출물로 취급하지 않았다.** 기능이 3개일 땐
아무 배치나 괜찮지만, 8개가 되면 배치가 곧 사용성이다. 그 전환점을 미리 잡지 않았다.

**다음엔 이렇게**
- 기능 목록이 **5개를 넘을 것 같으면**, 코드보다 **화면 지도(메뉴 트리)를 먼저** 그린다.
- 내비게이션은 "사용자의 작업 순서"를 따른다. 이 앱의 정답은
  `EDA → 모델 생성 → 모델 평가 → 모니터링`이라는 **업무 흐름 그대로**였다.
- 자주 누르는 액션 버튼은 **스크롤과 무관한 고정 위치**에 둔다.

**📱 iPhone 앱에서는**
모바일은 화면이 좁아 재구성 비용이 웹보다 크다 (탭 추가 = 전체 흐름 재설계).
**첫 주에 `TabView` / `NavigationStack` 골격부터** 만들고 빈 화면으로 흐름을 클릭해 본다.
탭은 3~5개를 넘기지 않는다. 화면이 늘면 탭을 늘리지 말고 **계층을 깊게** 한다.

## L2. 임계값을 학습 데이터에서 산출했다 (조용한 방법론 버그)

**무슨 일이 있었나**
정상 데이터로 오토인코더를 학습하고, **같은 데이터**의 재구성 오차 99 백분위수를 임계값으로
썼다. 동작은 완벽히 "잘" 됐다. 사용자가 요청한 리뷰 단계에서야 이 편향을 발견했다.
학습에 쓰지 않은 정상 데이터(보정 분할)로 임계값을 산출하도록 고치자
**홀드아웃 오경보율이 2.9% → 1.4%** 로 바뀌었다 — 즉 이전 수치는 **과대평가**였다.

**근본 원인**
"데이터 누수 방지"를 `CLAUDE.md`에 원칙으로 적어 두고도 **스케일러에만 적용**했다.
임계값도 데이터에서 학습되는 파라미터라는 점을 놓쳤다. 게다가 버그가 **에러를 내지 않고
좋은 숫자를 냈기 때문에** 아무 신호도 없었다.

**다음엔 이렇게**
- **"데이터에서 산출되는 모든 값"** 목록을 만든다: 가중치, 정규화 파라미터, 임계값,
  클리핑 범위, 인코딩 사전, 기본값. 각각 "어느 데이터로 fit 하는가"를 문서에 명시한다.
- **에러를 내지 않는 버그**를 잡는 방법은 하나뿐이다 — **결과가 좋을 때 의심하고,
  독립된 데이터로 다시 측정**한다.
- 성능 수치는 반드시 **"어떤 데이터에서 측정했는지"** 와 함께 기록한다.

**📱 iPhone 앱에서는**
Core ML 모델을 앱에 넣을 때 **정규화 파라미터·임계값은 모델과 한 세트**로 번들한다.
학습 노트북의 상수를 Swift 코드에 손으로 옮겨 적는 순간 두 값이 갈라진다.
앱에도 같은 종류의 "조용한 버그"가 있다 — 크래시 없이 **잘못된 화면을 보여주는** 상태.
로그가 아니라 **스냅샷 테스트/스크린샷 비교**로 잡는다.

## L3. 배포 환경을 가정하고 의존성을 고정했다

**무슨 일이 있었나**
Streamlit Cloud 배포가 `Error during processing dependencies!` 로 계속 실패했다.
원인은 두 가지였다. ① `tensorflow>=2.13,<2.17` 로 **상한을 핀** 했는데 클라우드의 Python
버전에 맞는 휠이 그 범위에 없었다. ② 데모에 전혀 필요 없는 `oracledb`, `SQLAlchemy`가
설치 대상에 섞여 있었다. `tensorflow-cpu` + 상한 제거 + DB 의존성 파일 분리로 해결
(`f35e57c`).

**근본 원인**
내 개발 환경에서 되는 조합을 "정답"으로 고정했다. **상한 핀은 미래의 환경을 배제**하는
행위인데 그 비용을 몰랐다. 그리고 **선택 기능의 의존성을 필수 의존성에 섞었다.**

**다음엔 이렇게**
- 의존성은 **하한 위주**로 쓴다. 상한은 실제로 깨진 버전을 확인했을 때만 건다.
- **선택 기능(DB, 클라우드, 분석)의 의존성은 별도 파일**로 분리한다
  (`requirements.txt` / `requirements-db.txt`).
- 배포 전 **완전히 깨끗한 가상환경에서 설치를 재현**한다. 로컬에서 되는 것은 증거가 아니다.
- 무거운 패키지는 경량 변형이 있는지 본다 (`tensorflow` → `tensorflow-cpu`).

**📱 iPhone 앱에서는**
Swift Package Manager는 기본이 `upToNextMajor` 라 비슷한 함정이 있다.
더 중요한 건 **iOS Deployment Target** — 최신 API를 무심코 쓰면 지원 기기가 잘려 나가고,
그 사실은 **심사 단계나 사용자 리뷰에서** 드러난다.
시뮬레이터만 믿지 말고 **실기기 + 가장 낮은 지원 OS 버전**에서 주기적으로 빌드한다.

## L4. 테스트 데이터가 너무 쉬웠다 — 모든 모델이 만점을 받았다

**무슨 일이 있었나**
합성 정상/이상 데이터를 만들었는데 이상이 너무 뚜렷해서 **어떤 설정으로 학습해도
F1 0.95 이상**이 나왔다. 모델 비교 화면, 하이퍼파라미터 튜닝, 임계값 정책 — 전부
**변별력이 0**이라 무의미했다. 난이도(쉬움/보통/어려움)를 설계해 넣은 뒤에야
F1이 **0.934 / 0.925 / 0.731** 로 벌어지며 기능들이 의미를 갖기 시작했다.

**근본 원인**
테스트 데이터를 "파이프라인이 도는지 확인하는 용도"로만 생각했다. 실제로는 테스트
데이터가 **평가 기능 전체의 해상도를 결정**한다. 쉬운 데이터에서는 좋은 설계와 나쁜
설계가 같은 점수를 받는다.

**다음엔 이렇게**
- 테스트/데모 데이터는 **경계 사례를 의도적으로 포함**해 설계한다
  (약한 신호, 점진적 열화, 결측, 다중 운전 모드).
- **"모든 조건에서 결과가 좋다"** 는 성공이 아니라 **측정 도구가 고장났다는 신호**다.
- 난이도를 **조절 가능한 파라미터**로 만들어 두면 회귀 테스트에도 재사용된다.

**📱 iPhone 앱에서는**
같은 함정이 **목업 데이터**에 있다. 이름 3글자, 항목 5개, 사진 1장으로만 테스트하면
긴 한글 이름, 항목 500개, 빈 목록, 네트워크 없음, 다크 모드, Dynamic Type 최대 크기에서
레이아웃이 무너진다. **SwiftUI Preview를 극단값 세트로 여러 개** 만들어 두는 게
가장 값싼 보험이다.

## L5. 프레임워크의 실행 모델을 늦게 이해했다

**무슨 일이 있었나**
Streamlit은 상호작용마다 **스크립트 전체를 위에서 다시 실행**한다. 이걸 체화하기 전까지
상태가 사라지거나, 캐시가 잘못 잡히거나, 모델을 바꾸면 슬라이더 범위가 옛 값을 들고 있어
에러가 나는 문제를 **반복해서 사후 수정**했다.

**근본 원인**
"UI 라이브러리는 대충 비슷하겠지"라고 가정했다. 실제로는 **상태를 어디에 두는가**가
프레임워크마다 완전히 다르고, 그걸 모르면 모든 버그가 처음 보는 버그가 된다.

**다음엔 이렇게**
- 새 프레임워크는 **"언제 다시 그려지는가 / 상태는 어디에 사는가"** 두 질문의 답을
  첫날에 확보한다. 이게 나머지 버그의 절반을 없앤다.
- 상태에서 파생되는 위젯(범위, 기본값, 선택지)은 **소스가 바뀌면 함께 무효화**한다.
- 비용이 다른 캐시를 구분한다 (Streamlit: `@st.cache_data` vs `@st.cache_resource`).

**📱 iPhone 앱에서는**
**SwiftUI가 정확히 같은 계열의 함정**이다. `body`는 상태가 바뀔 때마다 재평가되고
뷰는 값 타입이다. `@State` / `@StateObject` / `@ObservedObject` / `@Observable` /
`@Binding`의 **소유권 차이**를 모르면 "값이 초기화되는" 버그를 계속 만난다.
규칙: **소유는 `@StateObject`(또는 `@State`), 전달은 `@ObservedObject`/`@Binding`.**
`body` 안에서 네트워크 호출·무거운 계산을 하지 않는다 (몇 번 불릴지 모른다).

## L6. 구조를 바꾼 뒤 옛 UI를 지우지 않았다

**무슨 일이 있었나**
좌측 4메뉴로 재구성하면서 "저장된 모델"·"샘플 데이터" 기능을 각 페이지 안으로 옮겼는데,
**사이드바의 기존 위젯을 지우지 않아** 같은 기능이 두 곳에 존재했다. 사용자가 직접
"중복이니 정리해 달라"고 지적했다 (`67cf314`).

**근본 원인**
"추가"는 눈에 보이고 **"삭제"는 눈에 보이지 않는다.** 새 구조가 동작하는 걸 확인한
시점에서 작업이 끝났다고 느꼈다.

**다음엔 이렇게**
- 구조 변경은 **`이동 = 추가 + 삭제`** 로 정의한다. 삭제 전엔 완료가 아니다.
- 재구성 후 **직접 화면을 끝까지 클릭**해 본다. 코드 diff로는 중복이 잘 안 보인다.
- 옮긴 기능은 **원래 자리에 남아 있지 않은지** 체크리스트로 확인한다.

**📱 iPhone 앱에서는**
같은 액션이 탭바·툴바·컨텍스트 메뉴·스와이프에 **중복 배치**되기 쉽다.
기능당 **"주 진입점 1개 + 보조 1개까지"** 를 원칙으로 둔다.

## L7. 사용자가 누르지 않은 비싼 동작을 자동 실행했다

**무슨 일이 있었나**
앱을 열면 **자동으로 학습이 시작**되도록 만들었다. 사용자는 "초기 로딩에서는 학습하지 말고,
CSV를 올린 뒤 **학습 버튼**을 눌러 진행하게 해 달라"고 명확히 요청했다 (`93bbc65`).

**근본 원인**
"바로 결과를 보여주면 좋겠지"라는 **개발자 편의의 데모 사고**. 사용자 입장에서 학습은
시간·자원을 쓰는 **되돌릴 수 없는 작업**이고, 시작 여부는 사용자가 결정해야 한다.

**다음엔 이렇게**
- 비용이 드는 작업(학습, 대용량 처리, 외부 전송, 과금)은 **항상 명시적 실행**으로 만든다.
- 대신 **진행률과 취소**를 제공한다. 자동 실행보다 예측 가능성이 가치가 크다.

**📱 iPhone 앱에서는**
`onAppear`에서 네트워크 요청·권한 요청·결제·위치 추적을 시작하지 않는다.
특히 **권한 팝업을 첫 화면에서 띄우면 거절률이 급등**한다 — 그 권한이 필요한 기능을
사용자가 누른 **직후**에, 왜 필요한지 먼저 설명하고 요청한다.

## L8. UI 자동화 테스트를 깨지기 쉬운 방식으로 짰다

**무슨 일이 있었나**
Playwright로 화면을 검증하다가 반복해서 실패했다. 숨겨진 업로더 때문에
`input[type=file]` **인덱스**가 밀렸고, `text=데이터 분석 결과` 같은 **문구 셀렉터**는
문구가 바뀌자 죽었으며, **렌더링 도중 스크린샷**을 찍어 빈 화면을 얻었다.
정리하려고 실행한 `pkill -f "streamlit run"` 이 **내 셸까지 종료**시킨 적도 있다.

**근본 원인**
테스트가 **UI의 표현(문구·순서)** 에 의존했다. 표현은 가장 자주 바뀌는 부분이다.

**다음엔 이렇게**
- 테스트는 **전용 식별자**로 요소를 찾는다. 문구·인덱스·CSS 경로에 의존하지 않는다.
- **"로딩이 끝났음을 뜻하는 실제 콘텐츠"** 가 나타날 때까지 기다린 뒤 검증한다.
  고정 `sleep`은 느리면서도 불안정하다.
- 프로세스를 죽이는 명령은 **패턴이 자기 자신을 잡지 않는지** 먼저 확인한다.

**📱 iPhone 앱에서는**
XCUITest에서 `accessibilityIdentifier`를 **UI를 만들 때 같이 부여**한다
(레이블 텍스트로 찾지 않는다 — 번역·문구 변경에 죽는다).
덤으로 이 식별자 작업이 **VoiceOver 접근성**을 동시에 개선한다.

## L9. 브랜치·배포 전략을 프로젝트 중반에 정했다

**무슨 일이 있었나**
PR을 열려고 보니 저장소에 **브랜치가 하나뿐이고 그게 기본 브랜치**여서 base가 없었다.
급히 `main`을 만들어 PR을 열었다. 별도로, 원격에 다른 커밋이 있어 **push가 거절**된 적도
있다 (`git fetch` + `rebase`로 해결).

**근본 원인**
"코드부터 쓰고 나중에 정리하자"고 미뤘다. 협업 구조는 **나중에 바꾸면 히스토리가
지저분해지는** 종류의 결정이다.

**다음엔 이렇게**
- **첫 커밋 전에** 기본 브랜치 + 작업 브랜치 + PR 흐름을 정한다.
- `push` 전엔 **항상 `fetch` 후 최신 상태를 확인**한다.
- 대용량 산출물(데이터, 모델, 빌드)은 처음부터 `.gitignore`에 넣는다.

**📱 iPhone 앱에서는**
여기에 **`.gitignore`(DerivedData, `xcuserdata`, `*.xcuserstate`)** 와
**`project.pbxproj` 충돌 전략**을 추가한다. 이 파일은 병합 충돌이 잦아 팀이면 고통스럽다.
서명 인증서·프로비저닝 프로파일 관리 방식(자동 서명 / fastlane match)도 초기에 정한다.

---

## L10. 로컬에만 있던 작업본이 사라질 뻔했다 (오늘 실제로 발생)

**무슨 일이 있었나**
이 회고를 쓰기 직전, 작업 환경이 초기화되어 **로컬 저장소가 첫 커밋 상태로 되돌아가** 있었다.
34개 커밋 분량의 작업이 로컬에서 사라졌지만, **원격에 모두 push 되어 있어 손실은 0**이었다
(`git reset --hard origin/<branch>` 한 번으로 복구).

**근본 원인**
없음 — **이건 습관이 통한 사례다.** 다만 "작업 단위가 끝날 때마다 커밋·push"를
지키지 않았다면 며칠치 작업이 사라졌을 상황이었다.

**다음엔 이렇게**
- **의미 있는 단위가 끝날 때마다 커밋하고 push 한다.** 완벽해질 때까지 기다리지 않는다.
- 로컬 디스크는 **캐시**로 취급한다. 원격에 없는 것은 존재하지 않는 것으로 본다.
- 환경(컨테이너·클라우드 IDE)은 언제든 초기화될 수 있다고 가정한다.

**📱 iPhone 앱에서는**
코드 외에 **시뮬레이터·기기에만 있는 것**을 조심한다: 테스트 데이터, 스크린샷,
`UserDefaults` 설정. 앱 삭제·기기 변경으로 사라진다.
**저장 위치(UserDefaults / 파일 / Core Data / Keychain / iCloud)를 기능 설계 시점에**
정한다. 나중에 옮기려면 마이그레이션 코드가 필요하다.

## L11. 부분적으로 쓰다 만 데이터를 정리하지 않았다

**무슨 일이 있었나**
학습이 중간에 중단되면 **비어 있는 모델 폴더**가 남아 모델 목록을 오염시켰다.
불완전 항목을 정리하는 함수(`registry.prune_incomplete`)를 나중에 추가했다.

**근본 원인**
**성공 경로만 설계**했다. 중단·크래시는 정상 시나리오의 일부인데 예외로 취급했다.

**다음엔 이렇게**
- 여러 파일을 함께 쓰는 작업은 **"전부 성공 또는 흔적 없음"** 으로 설계한다
  (임시 폴더에 쓰고 마지막에 이름 변경, 또는 완료 표시 파일).
- 시작 시 **불완전 상태를 감지·정리**하는 경로를 만든다.

**📱 iPhone 앱에서는**
앱은 **언제든 강제 종료**된다(백그라운드 회수, 스와이프 종료, 크래시).
다운로드·편집 중 상태가 반쯤 저장되는 걸 전제로 설계한다.
파일은 원자적 쓰기, Core Data는 저장 시점을 명확히, **재시작 시 복구 경로**를 만든다.

---

## L12. 산출물의 "보관 위치"를 합의하지 않았다

**무슨 일이 있었나**
진행 상황 스크린샷을 대화로만 전달했다. 사용자가 "저장소에 커밋하고 README에서
링크해 달라"고 요청해서야 `docs/screenshots/`에 넣었다.
문서도 비슷하게, 앱 내 도움말과 md 파일이 따로 놀 뻔해 **md를 단일 소스로 두고
앱이 렌더링**하는 구조로 정리했다.

**근본 원인**
"전달했다"와 "남겼다"를 혼동했다. **대화는 휘발되고 저장소만 남는다.**

**다음엔 이렇게**
- 산출물(스크린샷, 결정 기록, 성능 수치)은 **저장소 안 정해진 위치**에 남긴다.
- 같은 내용이 두 곳에 있으면 **한쪽을 원본으로 정하고 나머지는 렌더링/참조**한다.
  복붙된 문서는 반드시 갈라진다.
- 결정 사항은 **"왜 그렇게 정했는지"** 와 함께 기록한다. 3주 뒤의 나는 이유를 잊는다.

**📱 iPhone 앱에서는**
디자인 결정, 스크린샷, App Store 문구, 심사 대응 기록을 저장소에 남긴다.
특히 **심사 리젝 사유와 대응**은 다음 릴리스에서 그대로 다시 쓰인다.

# 2부. 잘 작동해서 계속 유지할 습관

1. **원칙을 문서로 먼저 고정했다** — `CLAUDE.md`의 8대 설계 원칙(데이터 누수 방지,
   불균형 평가, 아티팩트 세트 등)이 수십 번의 판단 기준이 됐다.
   → 새 프로젝트에서도 **"절대 어기지 않을 원칙 5~8개"** 를 첫날에 쓴다.
2. **실제로 실행해서 확인했다** — 브라우저를 띄워 클릭하고 스크린샷으로 검증했다.
   "코드상 맞다"와 "화면에서 동작한다"는 다른 주장이다.
3. **주장 대신 수치를 냈다** — "개선됐다"가 아니라 "오경보율 2.9% → 1.4%".
   숫자가 없으면 개선인지 확인할 방법이 없다.
4. **로직과 UI를 분리했다** — `src/`(순수 로직) / `app/`(화면). UI를 세 번 갈아엎는 동안
   `src/`는 거의 그대로였다. **이 분리가 재구성 비용을 감당 가능하게 만든 결정적 요인**이다.
   → 📱 iPhone에서도 동일: **모델·로직은 SwiftUI에 의존하지 않는 순수 Swift**로.
      뷰는 자주 바뀌고 로직은 오래 산다.
5. **산출물을 한 세트로 버전 관리했다** — 모델 + 스케일러 + 임계값 + 스키마 + 메타데이터.
   하나라도 빠지면 재현이 안 된다는 걸 전제로 설계했다.
6. **되돌리기 어려운 결정은 물어봤다** — 프레임워크 선택, 브랜치 생성, 알림 정책 등.
7. **변경 이력을 남겼다** — `CHANGELOG.md` / `ROADMAP.md`로 "어디까지 왔고 다음이 무엇인지"를
   매번 복원할 수 있었다.

# 3부. iPhone 앱을 만들 때 추가로 대비할 것

이 프로젝트에는 없었지만, 모바일에서 **같은 성격의 실수**가 나타나는 지점들이다.

| 이 프로젝트의 교훈 | iPhone 앱에서의 대응물 |
|---|---|
| 배포 환경을 가정했다 (L3) | **기기·OS 파편화** — 최소 지원 iOS, 작은 화면(SE), 큰 글꼴, 다크 모드 |
| 실행 모델을 늦게 배웠다 (L5) | **SwiftUI 상태 소유권** + `async/await` / `@MainActor` 동시성 |
| 자동 실행이 문제였다 (L7) | **권한 요청 타이밍** (위치·알림·사진·카메라) — 맥락 안에서 요청 |
| 영속성 모델이 늦었다 (L10) | **저장소 선택**을 기능 설계 시점에 (UserDefaults / 파일 / Core Data / Keychain / iCloud) |
| 부분 쓰기 (L11) | **앱 강제 종료·백그라운드 회수**를 전제로 한 저장 |
| 산출물 위치 (L12) | **심사 자산**(스크린샷·개인정보 라벨·권한 설명 문자열)을 저장소에서 관리 |

**모바일 고유로 초기에 정해야 할 것**
- **출시 요건을 개발 전에 확인한다** — 권한 사용 설명(`Info.plist` 문자열),
  개인정보 라벨, 계정 삭제 기능, 로그인 제공 시 Sign in with Apple 요건.
  이걸 나중에 알면 **완성된 앱이 심사에서 막힌다** (L3의 "환경 가정" 실수와 같은 구조).
- **오프라인/네트워크 실패를 기본 시나리오로** 설계한다. 웹앱보다 훨씬 자주 발생한다.
- **배터리·메모리 예산**을 의식한다. 백그라운드 작업, 이미지 캐시, 타이머.
- **접근성(Dynamic Type, VoiceOver)** 을 처음부터 넣는다. 나중에 넣으면 레이아웃을 다시 짠다.
- **TestFlight 배포 경로를 초반에 한 번 뚫어 둔다.** 인증서·프로비저닝 문제는
  마감 직전에 발견하면 가장 비싸다 (L3, L9의 교훈이 그대로 적용된다).

# 4부. 새 프로젝트 킥오프 체크리스트 (복사해서 사용)

### 코드를 쓰기 전 (30분)
- [ ] **절대 원칙 5~8개**를 문서로 적는다 (이 프로젝트의 `CLAUDE.md`에 해당)
- [ ] **화면 지도**를 그린다 — 메뉴/탭 구조를 사용자의 작업 순서대로
- [ ] **기본 브랜치 + 작업 브랜치 + PR 흐름** 확정
- [ ] **`.gitignore`** 에 대용량 산출물·빌드 결과·자격 증명 추가
- [ ] **자격 증명은 환경변수/보안 저장소**, 저장소에는 예시 파일만
- [ ] **저장 위치(영속성) 결정** — 무엇을 어디에 얼마나 오래 저장하는가
- [ ] **출시/배포 요건**을 먼저 읽는다 (스토어 심사 요건 / 배포 환경 제약)

### 첫 주
- [ ] 프레임워크의 **"언제 다시 그려지나 / 상태는 어디 있나"** 를 확인한다
- [ ] **로직과 UI를 분리**하는 폴더 구조를 잡는다
- [ ] **빈 화면으로 내비게이션 전체**를 클릭해 본다
- [ ] **깨끗한 환경에서 빌드/설치 재현** (실기기 또는 새 가상환경)
- [ ] **테스트용 극단 데이터** 세트를 만든다 (빈 값, 매우 긴 값, 대량, 실패 응답)
- [ ] UI 요소에 **안정적 식별자**를 부여하기 시작한다

### 개발 중 반복
- [ ] 의미 있는 단위마다 **커밋 + push** (로컬은 캐시일 뿐이다)
- [ ] 결과가 **너무 좋으면 측정 방법을 의심**한다
- [ ] 구조를 바꿨으면 **옛 UI를 지웠는지** 확인한다
- [ ] 비싼 동작은 **사용자가 누를 때만**, 진행률·취소 제공
- [ ] 개선은 **수치로** 기록한다 (전/후, 측정 데이터 명시)
- [ ] 결정은 **이유와 함께** 저장소에 남긴다

### 릴리스 전
- [ ] 중단·크래시 후 **재시작 복구 경로** 확인
- [ ] 최소 사양 환경에서 동작 확인
- [ ] 접근성(글꼴 확대, 스크린리더) 확인
- [ ] 문서/도움말이 **현재 동작과 일치**하는지 확인
